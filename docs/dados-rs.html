1 · Arquitetura atual e por que migrar

Hoje: arquivo único index.html (~44 KB), sem back-end nem build. Roda 100% no navegador, faz fetch direto no endpoint do SIGDC (que devolve Access-Control-Allow-Origin: *), guarda a última resposta em localStorage e cobre 4 pontos de Eldorado do Sul.

Limites que forçam a migração:

  • Só funciona porque o SIGDC libera CORS — as demais fontes (ANA, SGB/SACE, INMET) não liberam, e a ANA ainda exige token OAuth. Sem back-end, é impossível agregá-las.
  • Dezenas/centenas de pontos estaduais exigem catálogo, normalização e histórico — inviável hardcoded num HTML.
  • Sem banco não há série histórica própria, tendência confiável, nem alertas/push.
  • Um único arquivo cresce sem testes, sem componentização e sem cache de servidor.

5 · A questão do CORS / proxy

Ponto de decisão central. O modelo atual (fetch direto do navegador) só é possível porque o SIGDC libera CORS. ANA (OAuth), SGB/SACE, INMET e CEMADEN não — e do lado servidor vários respondem 403 a fetch automatizado. Conclusão: qualquer expansão além do SIGDC exige um proxy/back-end próprio que (a) guarde o token OAuth da ANA, (b) normalize as fontes num schema único, (c) faça cache, e (d) devolva JSON com CORS liberado para o front.

6 · Recomendação de migração

Preservando o excelente trabalho de acessibilidade e performance mobile já existente, a rota recomendada é faseada — não um rewrite de uma vez.

Fase 1 — Camada de dados (sem tocar no front)
Subir um proxy serverless (Cloudflare Worker ou Vercel Function) que centraliza as fontes, guarda o token OAuth da ANA, normaliza tudo no schema que o app já usa (ponto → leitura, cotas, histórico, tendência) e devolve JSON com CORS *. Cache em KV. Já destrava a ANA e a cobertura estadual. O index.html atual passa a apontar para o proxy.
Fase 2 — Histórico e agendamento
Banco Postgres (Supabase, free tier) para série histórica própria e tendência confiável; ingestão agendada (cron do Worker) puxando ANA/SACE/Open-Meteo a cada ~15 min. Abre caminho para alertas.
Fase 3 — Front componentizado
Reescrever a UI em SvelteKit (ou Astro com ilhas) — bundle mínimo, essencial num app de emergência acessado por celular em cheia. Migrar os tokens de design e as regras de acessibilidade já definidos. Adicionar mapa dos pontos e web-push de alertas.

Stack recomendada (opinativa)

Duas opções coerentes. Dado o peso do painel de moderação de admins e o requisito futuro de IA, a opção A (Laravel) é a preferida — unifica tudo num stack só.

Opção A — Laravel (recomendada)
Um framework resolve quase todos os requisitos de uma vez:
  • Painel admin: Filament (ou Nova) entrega fila de moderação, aprovar/rejeitar, auth e papéis quase de graça — atende direto o relato fotográfico do cidadão.
  • Ingestão: task scheduler puxa ANA/SACE/Open-Meteo a cada ~15 min; queues processam uploads e a fila de moderação.
  • Proxy/OAuth + storage: Http client guarda/renova o token da ANA e normaliza as fontes; Storage cuida das fotos.
  • Banco: Eloquent + Postgres para histórico e tendência.
  • IA (fase futura): pacote first-party laravel/ai — API única e provider-agnostic (inclui Anthropic/Claude), com agents, tools, structured output e streaming. Ver nota abaixo.
  • Front público: manter leve — Blade + JS mínimo, ou um front separado (Svelte), sem Livewire pesado na página de emergência.
  • Hospedagem: servidor PHP (Forge / DigitalOcean / Laravel Cloud). Custo fixo baixo, mas não é serverless grátis.
Opção B — Serverless JS
SvelteKit (front) + Cloudflare Worker/Cron em TypeScript (proxy + ingestão + cache KV) + Supabase/Postgres (histórico) + Open-Meteo direto. Custo ~zero e CDN nativo, mas o painel de moderação e a futura IA ficam por conta própria (mais peças costuradas à mão).
IA destravada por SDK nativo. Com laravel/ai (first-party), a fase de validação por visão — adiada de propósito — deixa de exigir serviço Python à parte. Structured output devolve algo como { é_agua: bool, confiança, descrição }, pronto pra gravar e exibir no painel; vision via Anthropic faz a classificação; tools/agents podem, mais adiante, pré-triar relatos antes da fila. Segue como evolução da Fase 3+ — não antecipar na v1.
Atalho de baixo atrito (pode entrar já na Fase 1): adicionar Open-Meteo (chuva + vazão GloFAS) aos cards atuais cabe no arquivo único e não precisa de back-end — é o primeiro ganho visível.

7 · Requisito futuro — relato fotográfico do cidadão

Um visitante não cadastrado poderá tirar/enviar uma foto de um ponto de rio e associá-la a uma localização. Decisões já tomadas para a primeira versão:

  • Localização por geoposicionamento, não por EXIF. Usar navigator.geolocation (com permissão do usuário) como fonte de coordenada — mais confiável que o GPS do EXIF, que some na maioria dos envios mobile (Safari, galeria, prints, imagens que passaram por apps de mensagem). EXIF fica, no máximo, como fallback secundário.
  • Sem IA neste primeiro momento. Nada de classificação automática de “é imagem de nível de água?”. Fica registrado como evolução posterior (modelo de visão), mas fora do escopo inicial.
  • Filtro = painel de validação de admins. Todo envio entra numa fila de moderação e só é publicado após aprovação manual de um administrador. O painel é a barreira contra conteúdo impróprio, irrelevante ou falso.

Fluxo

visitante anônimo
  → captura/seleciona foto  +  navigator.geolocation (coordenada)
  → envio (upload) para o back-end
  → fila de moderação (pendente)
  → PAINEL ADMIN: aprova | rejeita
  → se aprovado: publicado como "relato de cidadão"
       (separado visualmente da telemetria oficial)
Relato ≠ leitura de sensor. Coordenada e imagem enviadas por anônimo são forjáveis; durante cheia, um dado falso é perigoso. O relato aprovado deve aparecer sempre rotulado como relato do cidadão, nunca como cota/medição oficial, e nunca disparar alerta sozinho.
LGPD. Foto pode conter rosto, placa ou localização de residência; a geolocalização é dado pessoal. Exigir consentimento no envio, definir política de retenção, e remover metadados sensíveis do que for armazenado/exibido. Manter os relatos anônimos de fato (sem vincular a identidade).
Impacto na arquitetura. Upload de imagem, storage, fila e painel de moderação não rodam só no navegador — este requisito depende da camada de back-end da Fase 1/2. O painel de admin é a única parte com autenticação (só administradores); o envio do visitante permanece sem cadastro.
